# The Golden Set is a stratified holdout queue hand-labelled from the full transcript

`docs/specs-v0.md` section 8 asks for a 150-250 example human-labelled Golden Set with `customer_message`, gold intent, gold auto/escalate, and notes; decision 13 fixes the shape: proportional across intents with a ~10-example per-intent floor and a ~60/40 auto/escalate balance; decision 6 says the set is drawn only from the holdout, so no golden example can be retrieved as evidence for itself. Ticket 18 builds the labelling CLI, ticket 19 completes the labelling.

The holdout carries no intent labels and the floors are per intent, so sampling needs hints. The configured `labeler` role predicts one intent and one coarse auto/escalate decision per holdout message, cached by prompt hash in a crash-safe append-only file (the same mechanism as ADR-0007 and ADR-0009). Hints only choose *which* Interactions get served: they are never shown to the human labeller and never become gold. The hint rubric is deliberately not the ticket-14 classifier or the ticket-21 policy — it is a sampling aid that goes stale, and the report records predicted-versus-gold agreement so its bias is visible. An explicit `--hints` file with `prompt_sha256: null` entries is accepted, so a later ticket's classifier can drive stratification without changing this stage.

The labeler is a reasoning model, and a sampling hint needs no chain of thought: the call passes `extra_body={"chat_template_kwargs": {"enable_thinking": false}}`, which cuts the recorded runs from ~1,000 completion tokens per hint to ~50. A flaky reply that is not a single JSON object is retried up to three attempts with a retry prompt that shows the rejected reply, and a transient API failure (rate limit, connection error) is retried with exponential backoff up to five attempts: one malformed reply or one 429 must not kill a 1,000-call run. The thinking toggle is provider-specific (NVIDIA NIM chat templates) and lives on this stage's `call_labeler`, not in `llm.call_llm` defaults.

Stratification is apportionment, not a roll of the dice. Each intent receives a quota proportional to its hinted volume, never below `--floor` (default 10) and never above what exists; when the floors alone exceed `--target` (default 200, inside the spec's 150-250), the floors win and the report says so. Within each quota, candidates are assigned to predicted-auto and predicted-escalate slots; the auto target (`--auto-share`, default 0.6) is clamped into the range the fixed quotas allow, and the sampling report states the requested and predicted balance plus whether the target was reachable there. That range is narrower than the whole holdout's capacity when a stratum is one-sided, so a one-sided corpus can land off the share or fail to meet it; the report makes that visible instead of trading away the per-intent proportions, and the labelling report records the achieved gold balance for ticket 19 to top up. Candidates are ranked by a SHA-256 of `seed:interaction_id`, like the sample/split stage, so selection is deterministic across input order and machines, and the choices with different seeds differ only when a stratum has more candidates than slots.

Two commands split planning from labelling. `query sample-golden` reads the holdout and taxonomy, obtains or reuses hints, and, when asked, writes `data/golden-queue.jsonl` (`{interaction_id, hint_intent, hint_decision}`) and `data/golden-sampling-report.json` (per-intent availability and selection, predicted balance, target-met); the console always reports the same counts. `query label-golden` serves the queue: the full Interaction with sides and timestamps, then a gold intent from a numbered final-taxonomy menu, a gold `auto`/`escalate` decision, and optional notes. The queue file is the audit trail for "stratified with a per-intent floor", and the labeler's session never sees the hints or a running decision balance, because both would bias the gold labels. `s` skips and `q` pauses at every prompt, and a session that ends without a completed label leaves no Golden Set file rather than an empty one.

Each completed label is swapped into the Golden Set file atomically before the next Interaction is shown, so `ctrl-c`, `EOF`, or `q` leaves a complete snapshot and the next session skips the ids already labelled. The Golden Set record is the spec's fields plus provenance: `{interaction_id, taxonomy_version, customer_message, gold_intent, gold_decision, notes, hint_intent, hint_decision}`. `reference_cases` from the spec is optional and omitted until a stage needs it; adding an optional field cannot break the reader. A Golden Set that contains an id outside the queue, or was labelled against a different taxonomy version, fails rather than silently mixing sets. The labelling report is the ticket-19 distribution artifact: per intent and per decision counts, notes coverage, and predicted-versus-gold agreement, keyed to `golden_set_version` and `taxonomy_version` so ticket 23 and ticket 25 can attach numbers to a version.

## Considered Options

- **Keyword heuristics for hints**: rejected. Floors computed from keyword strata would be nearly meaningless, and no keyword rule can predict auto/escalate well enough for the balance target to mean anything.
- **Embedding nearest-neighbour hints**: rejected. Local MiniLM is free and deterministic, but intents like `billing_payment` versus `subscription_plans` turn on meaning, not lexical proximity, and embeddings cannot produce a decision hint at all.
- **Require hints produced by tickets 12/14**: rejected. Those tickets are parallel work items; requiring their artifacts would block ticket 19 and make the CLI unable to run on a fresh checkout. The `--hints` seam keeps that integration open.
- **Ask the labeler to also emit a confidence and sample on it**: rejected. The floors and the balance target already decide the shape, and a confidence threshold would silently change the queue when the model changed.
- **Show the hint to the human labeller**: rejected. Agreement with the model would inflate the intent and decision metrics the Golden Set exists to measure.
- **One command that samples and labels**: rejected. The queue and sampling report are the reviewable evidence for the sampling acceptance criteria; keeping them as files matches the pipeline's stage-per-artifact convention and lets ticket 19 label later.
- **Append labels instead of rewriting**: rejected for a 250-record file. The atomic full rewrite reuses the writers' swap pattern and cannot leave a partial Golden Set.

## Consequences

- The Golden Set has traceability: every example records the taxonomy version it was labelled against and the hint that selected it, and the reports carry predicted-versus-gold agreement.
- The 60/40 target is enforced on predictions, not on gold labels; the labelling report states the achieved gold distribution, and ticket 19 can add examples for a side that lands short. An infeasible target (for example, too few predicted-auto candidates) is reported, never silently missed.
- The hints file is under the gitignored `data/`, one labeler call per holdout message, and is reused on reruns; a taxonomy or prompt edit invalidates entries by hash and recomputes them, like the other LLM caches.
- `llm.call_llm` gains an optional `extra_body` pass-through, used only here; other providers that reject the NVIDIA-specific thinking toggle would need that stage's call adjusted, not a pipeline change.
- The holdout stays reserved: nothing in this stage writes to the RAG pool or the resolution dataset, and the queue is the only bridge from the holdout to the Golden Set.
